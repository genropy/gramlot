# Rosetta v1 comparison

This is a comparison of three implementations of one deliberately small application.
The questions are whether the same behavior can run on FastAPI, how much code an
application author writes, and which integration costs currently remain visible.
It is not a framework ranking or a benchmark of a future Pages API.

## What is held constant

The backend, fixtures, editable fields, save/validation rules and common behavioral
checks are shared. React uses hooks and JSX; Vue uses Composition API and a
single-file component; Pages uses an existing Python recipe grammar and DOM JS.
React/Vue use native controls. Pages uses existing textBox, numberTextBox and
checkbox web components, with ordinary source-authored selection buttons.
Equivalent behavior is required, not pixel-identical component internals.

No version gets a grid, authentication, persistent database or unimplemented Pages
feature. Input timing is deliberately specified at blur: React/Vue can update on
each keystroke, while the existing Pages components commit on change.

## Observed authoring structure

| Concern | React | Vue | Pages |
| --- | --- | --- | --- |
| Interface | JSX | SFC template | Python source recipe, plus JS source mutation for list entries |
| Editable draft | useState updates | ref and v-model | Bag paths and component bindings |
| Local total | Derived expression | computed | dataFormula in the Python recipe, with a JS expression |
| Loading and saving | Async component functions | Async component functions | Explicit JavaScript controller |
| HTTP contract | Ordinary JSON | Ordinary JSON | Same JSON API; additional TYTX recipe request |
| Serving/build | Vite output mounted by FastAPI | Vite output mounted by FastAPI | Small FastAPI host and import map over existing source assets |
| Current installation | npm lock + shared Python lock | npm lock + shared Python lock | Shared Python lock plus local Pages/Builders/DOM source state |

Pages keeps field binding and the local formula close to the page description.
That is an observable convenience. It does **not** yet eliminate client glue in
this experiment: REST orchestration, saved/draft handling and startup live in the
JavaScript controller. A short Python recipe alone would hide part of the work.

The FastAPI adapter exercises a useful candidate boundary: the `WebPage` recipe
contract and DOM runtime can be used without running or installing genro-asgi.
However, this uses local source imports because the current Pages distribution
still declares genro-asgi mandatory. No production-ready agnostic package or
framework extraction has been implemented by this demo.

## Source inventory

The verified inventory is generated by `scripts/measure.py` and stored in
`docs/source-inventory.json`. It separates app code, host/browser adapters, shared
backend/style and setup. Counts use physical nonblank lines, including comments;
formatting differences matter. Lockfiles, generated builds, test code and library
internals are excluded. Adapters are visible costs, not subtracted as if they
already existed as reusable released features.

The Pages recipe is compact, but its recipe plus client controller currently total 244 nonblank lines, before the explicit host/browser adapters. React and Vue totals above include their client entry points. These numbers do not yet demonstrate less total authoring work for Pages.

Integrated validation passed 16 Python contracts and all 21 common Chromium scenarios. React and Vue production builds passed. Desktop (1100 px) and mobile (390 px) layouts were visually inspected; navigation among variants produced no JavaScript page errors. The shared suite now also checks visible product/price labels and selected-order ARIA state.

## Limits and next useful experiment

These implementations are generated examples reviewed against common behavior.
They do not establish how quickly an unfamiliar human learns each framework,
which code is most readable to the owner, or what an optimized implementation
would look like. No loading-speed or bundle-size ranking is claimed: Pages serves
raw development modules, whereas React/Vue use production bundles.

The next iteration should change the same behavior in all three apps and record
which files/concepts changed, using [the evolution protocol](EVOLUTION.md). A real
Pages grid can be added when it exists in its owning library; it is not simulated
here to improve the comparison. Later extraction of a reusable FastAPI adapter
would be a separate library decision, informed by this concrete consumer.

Implementation references used during setup:
[FastAPI static mounts](https://fastapi.tiangolo.com/tutorial/static-files/),
[React app setup](https://react.dev/learn/build-a-react-app-from-scratch), and
[Vue quick start](https://vuejs.org/guide/quick-start.html).
